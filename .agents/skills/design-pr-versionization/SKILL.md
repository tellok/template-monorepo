# 基于版本合并请求的发布设计

输出可审阅的发布设计，采用变更集（Changeset）和版本合并请求维护版本与变更日志，再由受信任流水线完成正式交付。此 skill 同时支持两个平台，但平台事件、YAML、令牌、执行审批和 API 分开维护，不相互套用。

## 先确定平台，再读取指引

1. 阅读项目协作规则、发布配置、包清单、锁文件、版本/发布脚本、现有流水线、下载入口及部署说明。区分当前实现、用户已选设计和待验证假设；发生冲突按目标项目规则处理。
2. 必读[共享发布契约](references/release-contract.md)。它定义版本准备、验证、正式交付和制品生命周期，不包含平台配置实现。
3. 按实际托管平台只读对应指引：
   - **GitHub Actions**：读 [GitHub 指引](references/github-actions.md)，先核对 `tellok/actions/github-actions/` 的可复用组件，再决定哪些缺口需要项目代码。
   - **GitLab CI/CD**：读 [GitLab 指引](references/gitlab-ci.md)，按目标实例版本和能力设计原生 MR 流水线、组件与 API。
   - 同时支持两平台时，分别产出两份平台方案，引用同一共享契约；不生成将两平台事件、审批或配置混在一起的模板。
4. 查明默认分支、实际 PR/MR 目标分支、发布单元、CLI 版本、执行器、缓存/制品存储及权限。除影响契约的缺失信息外，继续调查并记录假设。

## 始终保持的边界

- 版本 PR/MR 维护保持轻量：先检测未消费 Changeset，再隔离消费、生成版本/锁文件/CHANGELOG/来源记录及维护请求；不依赖产品构建，不提前发布。
- PR/MR 来源或实际目标更新都检查最新合并结果。来源更新优先用原生事件；仅补齐目标更新调度、取消旧检查及真实存在的其他缺口，不另造平台已有能力。
- 实际验证的源码、安装/构建/测试/校验脚本及验证配置来自同一待验收合并结果。可信控制层仅负责审批、调度、取消和身份核对，不以默认分支验证脚本替代来源修改。
- 正式构建前核实默认分支上的合法版本请求合并来源；验收一次，同一构建供全部正式消费者复用。
- 复用组件负责通用机制，调用方负责发布资格、版本单元、命令、来源证明、说明生成、存储、凭据及权限。不把某台执行器、挂载路径、桶或某项目布局写成通用默认。
- 运行许可与合并审批分开。优先平台原生执行信任政策，不默认要求全部协作者或机器人请求由所有者逐提交批准；补充入口也不能绕过外部贡献者的执行边界。
- 设计请求不授权实施流水线、修改秘密或远程设置、合并请求、发布版本、部署或删除远端文件。已有明确授权按其范围执行，不重复添加例行审批。

## 交付与验证

交付事件/阶段图、组件与项目职责、发布资格、版本/正文来源、检查身份和信任边界、存储与缓存、消费者及终态回收、并发与恢复方案。按[共享验收清单](references/release-contract.md#验收清单)和所选平台清单验证。

记录采用的组件完整提交、CLI/平台版本和文档核对日期；区分源码调查、本地检查、故障替身与真实平台实测。没有在目标平台跑过，不宣称该平台流水线已经生效。只声明实际选用的发布单元、包、架构与部署功能。
