# Spec Delta

## Purpose

让仓库的每个应用和共享包以独立语义化版本演进，并提供 GitHub 与 GitLab 可分别启用的质量流水线与发布设计，明确版本请求维护、合并结果验证和正式交付的授权及来源边界。

## ADDED Requirements

### Requirement: 独立版本与变更说明

项目 SHALL 使用变更集（Changeset）记录受影响包及语义化版本（Semantic Versioning, SemVer）级别；固定版本的 Changesets CLI MUST 生成对应版本、锁文件和中文变更日志，无固定或关联版本组。私有应用 MUST 可更新版本与日志但不上传 npm。

#### Scenario: 仅一个包有变更

- **WHEN** 在干净隔离副本消费只影响 webapp 的变更集
- **THEN** webapp 版本与日志更新，共享配置包版本不被无条件提升

### Requirement: 双平台质量入口

项目 SHALL 提供分开的 GitHub Actions 和 GitLab CI 配置，运行冻结安装、类型检查、测试及生产构建。请求检查 MUST 验收最新来源与实际目标的合并结果；平台不支持或结果过期时不得报告等价验收成功。

#### Scenario: 请求来源或目标变化

- **WHEN** PR/MR 来源或实际目标更新
- **THEN** 设计规定重新验证完整合并身份、取消过期检查，并维持外部贡献的执行许可边界

### Requirement: 轻量版本请求维护

发布设计 SHALL 在默认分支先检测存量未消费变更集，再准备版本 PR/MR；没有候选时跳过准备依赖和写入，有候选时只准备版本及来源记录，不构建或发布产品。

#### Scenario: 没有未消费变更集

- **WHEN** 目录仅含 README 或元数据
- **THEN** 版本维护跳过安装和写入，而必要请求重检仍按平台设计执行

### Requirement: 正式发布资格与同源交付

正式发布设计 SHALL 仅接受已核实的受管理版本请求合并，构建前核对来源、消费证据和实际版本；同一验收构建供全部消费者使用，临时制品与正式资产分离。普通提交、手工标签或仅有版本号 MUST 不自动获得发布资格。

#### Scenario: 普通默认分支提交

- **WHEN** 提交不是合法版本请求的合并
- **THEN** 可运行质量检查与版本维护，但不启动正式交付

### Requirement: 启用状态如实报告

项目 SHALL 记录两平台的权限、版本、执行信任、缓存、制品清理和恢复要求；未配置凭据、缺少目标实例或未实测时 MUST 标明未启用或未验证，不执行远程发布作为模板初始化验证。

#### Scenario: 模板尚未绑定发布目标

- **WHEN** 初始化完成但尚无目标包仓库或 GitLab 实例
- **THEN** 本地命令与配置检查结果单独报告，发布自动化保持关闭，文档给出启用条件
